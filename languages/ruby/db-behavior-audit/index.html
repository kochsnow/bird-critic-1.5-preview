PR #312 · User-ID query validation

Agent patch · GLM-5.2 / OpenCode
1 / 2DB behaviors passed
Audited issue descriptionIssue audit complete

Validating a user_id parameter in a query throws a 500 error. The lookup method used does not raise a record-not-found exception for missing users but instead silently returns nil, which then causes a NoMethodError when the code tries to access the id attribute on the nil result.

Audited task instruction · derived from the official PR issue description

Expected DB behaviors

  • DBB-312-1Valid lookup returns the persisted user ID.PASS
  • DBB-312-2Missing lookup raises ValidationError, not a nil dereference.FAIL

GLM-5.2 agent patch

Added a guard in an admin groups controller and a controller spec. The actual Data Explorer lookup in parameter.rb was untouched.

PR #37063 · Upload-reference lifecycle

Agent patch · GLM-5.2 / OpenCode
5 / 5DB assertions passed
Audited issue descriptionHuman-approved annotation

Object Settings Should Preserve Upload References

Upload references should be created for uploads stored inside object-type site settings and theme settings. These settings may store upload values as URLs in their serialized data, while upload-reference creation expects upload identifiers, so the save hooks need to resolve object upload values before maintaining references.

Continue to support existing upload and uploaded-image-list settings. For object schemas, find upload fields nested in the setting value, resolve their stored URLs to the corresponding uploads when possible, and keep upload references in sync so cleanup jobs do not remove uploads that are still used by settings.

Human-approved audited task instruction · derived from the official PR issue description

Expected DB behaviors

  • DBB-37063-1Site settings create upload references from URL-valued objects.PASS
  • DBB-37063-2Partial and full SiteSetting cleanup removes stale references.PASS
  • DBB-37063-3Theme settings create and fully clean upload references.PASS

GLM-5.2 agent patch

Converted upload URLs to IDs before creating references across SiteSetting and theme-setting models, with lifecycle tests across the affected surfaces.

Observed database state

Reference creation passed. SiteSetting cleanup moved 2 → 1 → 0; ThemeSetting cleanup reached 0. All five assertions passed.

Grounded diagnosis

The workspace patch was semantically correct even though the agent timed out during final verification before submit. The verifier evaluated the retained edits directly.

PR #592 · Group-destroy cleanup

Agent patch · GLM-5.2 / OpenCode
2 / 3DB behaviors passed
Audited issue descriptionIssue audit complete

When a group is deleted from the system, any topic assignments that were made to that group's members remain in place. There is no way to un-assign those users from the original group assignment after the group no longer exists.

Observed behavior

  • A group is created and members are assigned to topics through a group assignment.
  • The group is later deleted.
  • The topic assignments persist for all former group members.
  • There is no mechanism to remove or clean up these orphaned assignments.

Expected behavior

  • When a group is deleted, any assignments associated with that group should be cleaned up.
  • Users should not retain assignments from groups that no longer exist.
  • The system should not leave orphaned assignment records that cannot be managed.

Your task: Fix the issue so that deleting a group properly handles any existing assignments made through that group.

Audited task instruction · derived from the official PR issue description

Expected DB behaviors

  • DBB-592-1Destroying a group deletes its assignment rows.PASS
  • DBB-592-2Destroying a group synchronously removes related notifications.FAIL
  • DBB-592-3A control group’s assignments and notifications remain unchanged.PASS

GLM-5.2 agent patch

Added a before_destroy callback that scheduled an asynchronous notification cleanup job.

Observed database state

Target assignment rows reached 0, but notification rows remained at 2 when checked synchronously. Control-group rows persisted.

Grounded diagnosis

The patch was partially correct: assignment deletion worked, isolation held, and only lifecycle timing prevented notification cleanup from being immediately visible.

PR #36878 · Schema and target lookup

Agent patch · GLM-5.2 / OpenCode
2 / 3DB behaviors passed
Audited issue descriptionHuman-approved annotation

Admin Notice Dismissal With Missing Tracker Targets

When staff dismiss an admin notice that is backed by a problem-check tracker, dismissal should complete even if an older tracker row has an empty target value. Existing invalid tracker data must not cause a validation failure or return an unprocessable response while the notice is being dismissed.

The fix should also prevent the same invalid tracker state from being persisted for future problem-check tracking. Tracker records that represent checks without a concrete target should use the application's normal no-target representation consistently, and dismissing a notice should continue to reset or clear the associated tracker state as before.

Human-approved audited task instruction · derived from the official PR issue description

Expected DB behaviors

  • DBB-36878-1Migration eliminates persisted target IS NULL state.PASS
  • DBB-36878-2The target column is NOT NULL and rejects NULL inserts.PASS
  • DBB-36878-3Dismiss resets the tracker matching both identifier and target.FAIL

GLM-5.2 agent patch · exact replay

Normalized legacy NULL targets, added a NOT NULL constraint, and introduced model normalization. Runtime dismissal still searched by identifier only.

Observed database state

Legacy NULL rows reached 0; the constraint rejected a new NULL insert. Target-specific dismissal still selected the wrong tracker.

Grounded diagnosis

Exact patch replay separates correct migration/schema work from the missing application-level (identifier, target) lookup semantics.

Original 5-pilot findings

What behavior-level evidence made visible

In five behavior-level audited Ruby pilot cases, we observed partial database correctness, wrong-layer repairs, asynchronous lifecycle errors, and schema/runtime misalignment.

  1. 01

    Binary reward can hide partial correctness.

    Three unsuccessful patches still satisfied one or more observable database behaviors.

  2. 02

    Agents may repair the wrong software layer.

    A passing local test at the edited layer did not guarantee that the underlying data behavior changed.

  3. 03

    Lifecycle timing is part of semantics.

    Asynchronous cleanup was not equivalent to synchronously visible database state after the triggering action.

  4. 04

    Fixes can stop between application layers.

    Presentation, callback, query, migration, and runtime lookup layers did not always carry the same repair semantics.

  5. 05

    Schema correctness does not guarantee lookup correctness.

    A sound constraint and migration can coexist with an incomplete runtime selection predicate.

Scope and limitations

Audited pilots, not a population claim

The program now adds depth to 20 distinct Ruby-60 tasks. It does not estimate how often these failure modes occur elsewhere.

Two scoped pilots

The 5- and 15-case cohorts are non-overlapping subsets of the original Ruby-60—not additional benchmark instances.

Case-level evidence

Findings describe the 20 observed cases only and should not be generalized to all Ruby tasks.

Separate from leaderboard

This module validates tasks, verifiers, and patch semantics; it is not a second Ruby model ranking.

Grounding vs. correctness

A valid grounding may contain PASS and FAIL results. Validity means the result is attributable to the real patch.
