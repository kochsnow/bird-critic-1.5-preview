Audit overview

One protocol across heterogeneous stacks

The pilot hardens the audit method across Node/Strapi, Ruby/Rails, Python/Frappe, and PHP/Shopware/Sylius tasks. It is a purposive method-validation sample, not a Full-300 pass-rate estimate.

What was audited

Sixty evidence-linked persisted-state behaviors were executed through each project's native ORM, service, migration, or database path.

Canonical model cohort

GLM-5.3 × mini-swe-agent

Every final row binds the requested and served model, task checksum, network policy, exact workspace or replay, and verifier evidence. Infrastructure-invalid attempts stay visible but outside semantic comparison.

External replication

Shared audit pipeline

From release row to attributable state

Task and verifier changes are frozen before controls. Agent grading then reports F2P and every DBB jointly; reward alone never supplies a behavior-level conclusion.

Partner handoff

Rebuild, rerun, change model, review

The first release is a transparent replication package. Partners see the audit specification and verifier, while their coding model remains isolated from hidden evaluation artifacts and prior answers.

Interpretation boundary

What this pilot supports

The audit establishes executable case-level evidence and a reusable replication protocol. It does not establish a statistically representative Full-300 model score.

SupportedMethod portability

One DBB protocol worked across all six artifact profiles and four language ecosystems.

SupportedCase-level model diagnosis

Every canonical workspace has joint F2P and per-DBB attribution plus trajectory evidence.

SupportedExternal increments

A partner can hold the task/protocol fixed, change the model, and return a schema-compatible new row.

Not supportedPopulation inference

The 12 tasks were selected purposively; the displayed frequencies are descriptive only.
