Audit overview

One protocol across heterogeneous stacks

The pilot hardens the audit method across Node/Strapi, Ruby/Rails, Python/Frappe, and PHP/Shopware/Sylius tasks. It is a purposive method-validation sample, not a Full-300 pass-rate estimate.

What was audited

01

Analysis without a production edit

P02 spent 158 model calls tracing relation ownership, expanding a reproducer, and inspecting join tables, but timed out before changing persistence or repair code. Exact replay therefore grounds a no-production-fix result, not a setup failure.

02

Lifecycle or historical-state mutation

P03 converted “skip future processing” into deleting an already-persisted future row. P12 gave every old invoice a retroactive payment snapshot whose creation-time value was unknowable.

  • P03 · Discourse #36255
  • P12 · Sylius #246
03

Invocation or value-shape drift

P05's keyword-only service and enum representation diverged from the executable contract; its case card also records the instruction/test mismatch. P11's migration was perfect, but one call passed an Order object where a string was required.

  • P05 · Chatwoot #13796
  • P11 · Sylius #226
04

Incomplete schema contract

P06 implemented tables, relations, enums, validations, and cascades, yet omitted two collection columns required by the executable fabricator and reference schema. One schema gap prevented all 13 F2P examples and all seven DBBs from reaching their target assertions.

  • P06 · Mastodon #36977
05

Alternate architecture, wrong contract surface

P09 built and tested a functioning repair through its own subscriber namespace and dependency-injection wiring. The required class inherited a different constructor, so both direct construction and every DBB stopped at the boundary.

  • P09 · Shopware #15614
Task contract→Schema / migration→Model / service→Lifecycle path→Persisted state

The decisive variable was semantic propagation, not patch size. P04 completed a transactional multi-table merge; P11 completed a broad relation refactor but still failed one executable call; P12 passed every executable example while one historical-row invariant remained wrong.

Dual-layer audit

P11 and P12 disagree both ways

P11 is F2P FAIL / DBB PASS; P12 is F2P PASS / DBB MIXED. Neither executable tests nor persisted-state checks can substitute for the other.

Self-tests

DB-specific trajectory analysis

How the agent arrived at the database result

All twelve canonical trajectories are eligible for process analysis. They explain attention, observation, editing, verification, and stopping behavior; they do not override the case-card verdict.

Semantic authority

CASE_CARDS.md

Exact workspace, F2P result, every DBB assertion, confound check, replay fidelity, attribution, and joint grounding determine what the patch did.

Process evidence

DB_TRAJECTORY_ANALYSIS.md

DB understanding, reproduction, implementation, verification, non-DB overhead, direct observations, first production edit, and stopping condition explain how it happened.

01 · Effort

DB-heavy does not mean boundary-complete

P02 devoted 108 of 162 tool actions to DB-specific work but made no production edit. P03 devoted 113 of 115 actions to DB work yet encoded delete-not-preserve. P04's similarly DB-heavy run aligned its own transfer, deduplication, count, and rollback checks with all seven DBBs.

02 · Observation

The observed row and moment matter

P07, P08, and P10 queried the exact schema, boundary, and row transitions they needed to protect. P12 exercised a real MariaDB migration but never read the historical rows that carried its sole semantic failure.

03 · Feedback loop

Self-tests can close around the wrong frame

P05's 4,850 green examples, P06's 223 green examples, and P09's full Shopware dispatch test were substantial—but each reused the patch's own API, schema, or architecture, so internal consistency hid external contract drift.

04 · Attribution

Replay repairs measurement, not the patch

P02, P03, P05, P06, and P08 were evaluated through exact-patch replay after timeout, harness, fixture, credential, or provider confounds. No model request was repeated; the replay preserved the original patch while restoring a valid measurement path.

Partner handoff

Rebuild, rerun, change model, review

The first release is a transparent replication package. Partners see the audit specification and verifier, while their coding model remains isolated from hidden evaluation artifacts and prior answers.

01 · Select

Choose one pilot

Inspect its task, source commit, resource budget, image strategy, and publication checksum without building the other eleven.

02 · Anchor

Run cheap controls

Oracle 1.0 and NOP 0.0 must share the exact task checksum, with at least one semantic NOP DBB failure.

03 · Increment

Return the same schema

Submit exact patch/workspace, F2P and every DBB, five-category trajectory analysis, model identity, and evidence hashes.

Release-candidate package

Interpretation boundary

What this pilot supports

The audit establishes executable case-level evidence and a reusable replication protocol. It does not establish a statistically representative Full-300 model score.

SupportedMethod portability

One DBB protocol worked across all six artifact profiles and four language ecosystems.

SupportedCase-level model diagnosis

Every canonical workspace has joint F2P and per-DBB attribution plus trajectory evidence.

SupportedExternal increments

A partner can hold the task/protocol fixed, change the model, and return a schema-compatible new row.

Not supportedPopulation inference

The 12 tasks were selected purposively; the displayed frequencies are descriptive only.
