Benchmark Construction

Method

Every instance starts as a real GitHub pull request from a production repository — then goes through a verification gate and a human-in-the-loop rewrite before it's allowed into the benchmark.

  1. Filter ecosystems and collect real PRs

    We manually identify DB-related ecosystems and repositories, then collect merged pull requests from them — each one a real bug fix paired with the test that caught it, not a synthetic or LLM-authored task.

  2. Convert to Harbor and verify it's a real test

    Each candidate is converted into a runnable Harbor task and put through a gate: applying the reference patch (oracle) must make the test suite pass, and doing nothing (nop) must leave it failing. Instances that don't clear this bar are dropped.

  3. Rewrite the problem statement, then review it by hand

    Raw PR descriptions rarely name the exact files, classes, or interfaces an agent needs. We rewrite each instruction to spec-level detail — pinning down what the hidden test requires while withholding the actual implementation — and every rewrite goes through human quality review before it ships.

  4. Measure difficulty without moving the goalposts

    Lite 100 and Full 300 are fixed releases. We re-run the same instances to measure discrimination and analyze failures; harder verified tasks belong in a future version rather than silently changing the published splits.
